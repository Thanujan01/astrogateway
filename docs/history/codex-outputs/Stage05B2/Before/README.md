# AstroGateway Stage 05B identity API

Supabase Auth is the only identity issuer. Kotlin owns the SDK session. This API has no password, registration or token-minting endpoints. It verifies each bounded bearer token online with the configured Supabase `/auth/v1/user`, then checks issuer, authenticated audience/role, expiry, canonical user ID, Auth session UUID and verified email. Decoding alone is never accepted as authentication.

Application data lives in private `training`, following `outputs/Architecture/03_Data_API_And_Learning.md`. Do NOT expose this schema in Supabase Data API. A dedicated server-only PostgreSQL login, without superuser/BYPASSRLS/table ownership, is a member of NOLOGIN `astrogateway_api`. Every pooled transaction sets that restricted role and transaction-local verified user/session context. RLS also denies locally revoked Auth sessions. Neither Android nor Unity receives this database password or a service-role key.

## Configuration and migration (manual, not applied)

1. Reuse the existing approved TEST Supabase project. Review `../database/001_identity_and_mission_sessions.sql` in a disposable test project first. Apply once through an authorized SQL connection only after approval. It creates private schema/tables/policies and a profile trigger/backfill; no DROP or user/password edits. Name collisions must be reviewed rather than overwritten.
2. With an authorized administrator, provision a dedicated LOGIN role separately, setting its strong password through a secure administration channel. Grant `astrogateway_api` to it. Do not use postgres, schema/table owner or service_role as the runtime login. Keep runtime role distinct from migrations. A project/password secret is never checked in. Runtime startup rejects an unsafe role.
3. Provide HTTPS Supabase URL, publishable/anon key and SSL-capable pooler DSN via environment variables using `.env.example` as reference. This app does not automatically read `.env`. Prefer a secret manager/secure shell environment; never pass secrets on process command lines. Port 6543 transaction pooling is supported with prepared statement caching disabled. TLS is required.
4. Create a Python virtualenv, install `requirements.txt`. Run `uvicorn main:app --host 127.0.0.1 --port 8000 --no-access-log` from this directory with the approved environment. For deployed access, terminate HTTPS through an approved service; no deployment performed in Stage 05B. Do not log Authorization headers, URL callback parameters, request bodies, environment/driver exceptions or DSNs.
5. `GET /health` reports `configuration_required` until both provider and private DB are supplied. `GET /v1/me` returns the caller's profile. Mission initialization POST requires `{ "mission_id":"mission-red-horizon-poc", "launch_id":"UUID" }`. Completion POST requires `{ "launch_id":"same UUID", "outcome":"integration_check" }`. A bridge receipt earns no score or training level. Completion binds both caller and Auth session, is idempotent for the same completed launch, and rejects expired initializations.
6. `POST /v1/auth-session/revoke` immediately denies this Auth session to this API/private RLS even if its access JWT has time remaining. SDK sign-out separately revokes refresh capability. If offline, native state still clears; server revocation cannot be promised. Configure an appropriate short access-token lifetime (review 10–15 minutes), Supabase refresh rotation and anti-abuse/password/email settings. Revocation rows need periodic approved cleanup after expiry; none is scheduled here.

## Android configuration

Copy project-root `auth.local.properties.example` to ignored `auth.local.properties`, supply the SAME Supabase project and `auth.backendUrl`. Only URL/publishable key/API origin enter BuildConfig. Release requires HTTPS; debug accepts cleartext only to `10.0.2.2` for a local API, never Supabase. Rebuild after configuration. No actual credentials/configuration are included in the delivered APK.

Enable Supabase email/password provider. Review confirmation policy and SMTP sender/rate limits; this foundation requires verified email for private data/missions. With confirmation disabled Supabase normally supplies an already-confirmed user, but verify the real project's behavior. Add exact redirect `astrogateway://auth/callback` to authorized redirect URLs and ensure confirmation/recovery email templates perform the supported PKCE code exchange. Requests originate on the same Android installation; verifier and pending flow are encrypted and expire after one hour. Cross-device links must fall back to browser verification then sign-in; recovery must be requested on this device. Callback fragments containing tokens are rejected. Custom URI schemes can be claimed by other applications: PKCE protects code exchange, but a verified HTTPS App Link should replace the custom scheme before a public release once an owned domain is available.

Native encrypted state uses Android Keystore AES-GCM and AtomicFile in no-backup storage. Passwords remain transient input and are cleared on submission, excluded from saved state and screenshots; no password persistence. Lost/tampered keys fail closed. SDK logs are disabled. Host-managed serialized refresh avoids independent refresh-token rotations. Offline profile validation fails closed, preserving encrypted session only for retry; no offline authenticated mission launch.

Unity's private Activity receives version-1 launch JSON with mission ID, launch UUID, canonical user UUID, mission-session UUID and an expiring lease, never tokens. Existing C# ignores the added fields. The native broker submits only a correlated integration receipt. Sign-out/expiry requests return from Unity; future authenticated Unity actions must be allowlisted semantic commands mediated by the host, not arbitrary HTTP or credentials.

## Tests and limits

`pip install -r requirements-dev.txt` then `pytest tests -q`. These are isolated synthetic-token contract tests with a mock Auth transport, NOT live authentication. The accompanying local PostgreSQL WASM RLS checks validate SQL semantics, NOT a deployed Supabase project. Android test APK contains synthetic storage and mission-context fixtures only; it cannot establish a real account and is not shipped in the application APK.

Production readiness additionally requires live test accounts/confirmation/recovery tests, real refresh/revocation/second-account isolation, verified-domain App Links, rate limits at the API ingress, deployment TLS/secrets management, monitoring with redaction, and physical-device QA. No production migration/deployment was performed.
